# Codex for Open Source 路线

最后核对官方页面：2026-08-03  
官方申请页：<https://openai.com/form/codex-for-oss/>

## 1. 目标

把本项目做成一个真实解决问题、持续维护、可以被其他墨墨用户使用和参与的开源工具；在具备可信证据后，再申请 Codex for Open Source。

申请不是当前开发目标的替代品，也不能通过提前公开一个空仓库、制造提交数量或堆积无意义 Issue 来提高可信度。

## 2. 官方目前明确看什么

截至上述日期，官方页面明确要求或强调：

- 申请者是活跃开源项目的主要或核心维护者。
- GitHub 个人资料和申请仓库在申请时需要公开。
- 项目应有实质性使用、广泛采用，或对软件生态有明确重要性。
- 审核会看仓库使用情况、生态意义和持续维护证据。
- 维护证据可包括 PR 评审、Issue 分类、版本发布，以及安全和质量等持续责任。
- 入选者可能获得 6 个月 ChatGPT Pro（含 Codex）、面向维护工作的 API 额度，以及有条件的 Codex Security 访问。
- 申请滚动审核，不保证获选。

因此，本项目需要积累的是**真实产品价值和真实维护工作**，而不是形式上的公开状态。

## 3. 分阶段路线

### 阶段 0：短期私有清场

目标：避免第一轮 API 实验把 Token、私人词条或未脱敏响应写进公开历史。

完成条件：

- `AGENTS.md`、安全规则和 Issue backlog 已建立。
- 凭证只从环境变量或系统钥匙串读取。
- 能执行 dry-run，且第一次真实写入只涉及一条可丢弃数据。
- Git 历史检查无真实 Token 和私人学习数据。

该阶段应该短，不应以“等产品完全完成”为理由长期保持私有。

### 阶段 1：公开 v0.1

推荐首个公开能力：**安全的自建释义批量预览/录入**。

公开门槛由 Issue #6 管理，至少包括：

- 另一个用户可以按文档安装和运行。
- 有一条端到端闭环，而不是只有设计文档。
- README、License、Security、Contributing 和示例配置齐全。
- 核心解析与写入安全逻辑有测试。
- 例句线路如仍受阻，可以明确标记为 blocked，不应拖延释义线路公开。

### 阶段 2：真实使用和维护

需要主动但诚实地获得反馈：

- 发布版本并记录 release notes。
- 提供清晰的安装、dry-run 和故障排除说明。
- 接受真实 bug、兼容性问题和功能请求。
- 对 Issue 做分类、复现、关闭或转为后续计划。
- 对外部 PR 做审查并记录设计取舍。
- 建立稳定但不过度承诺的发布节奏。

“用户”不必一开始很多，但必须是真实的；可以从共同学习的伙伴和其他墨墨开放 API 使用者开始。

### 阶段 3：形成可核验的维护证据

Issue #7 作为证据总账，只记录可验证项目：

| 证据类型 | 可接受证据 | 不可接受做法 |
|---|---|---|
| 使用情况 | 真实安装、发布下载、使用反馈、可复现案例 | 自己反复下载、虚构用户 |
| 采用情况 | 外部用户长期使用、引用、集成或推荐 | 购买/交换 Star |
| Issue 维护 | 真实问题的复现、分类、修复和解释 | 创建无意义 Issue 再自行关闭 |
| PR 维护 | 外部贡献、代码审查、变更请求和合并记录 | 为制造数量拆分机械 PR |
| 发布维护 | 版本化发布、变更记录、迁移说明 | 空发布或只有版本号 |
| 安全与质量 | 凭证保护、测试、漏洞修复、兼容性工作 | 把普通格式化包装成安全工作 |
| Codex 使用 | 实际减少 triage、review、release 负担的流程 | 泛泛声称“用 AI 提效” |

### 阶段 4：准备并提交申请

申请前检查：

- GitHub Profile 为 Public。
- 仓库为 Public。
- 申请者能够准确说明自己是 Primary Maintainer。
- 至少有一个公开可用版本和非所有者真实用户。
- 维护历史足以支持“active open-source project”。
- 资格说明中的每个事实都有仓库、发布页或可核验数据支持。
- API 额度用途与开源维护直接相关。

## 4. 申请材料模板（现在不填数字）

官方表单目前包含每项最多约 500 字符的关键回答。数字和采用情况必须到申请时从真实数据填写。

### Why does this repository qualify?

建议结构：

1. 一句话说明它解决的具体、重复且普遍的问题。
2. 给出真实使用或采用证据。
3. 说明它为何补齐墨墨开放 API 生态中的缺口。
4. 说明主要维护者承担的 Issue、PR、发布和安全工作。

禁止提前写入尚不存在的 stars、downloads、users 或 ecosystem importance。

### How will you use API credits?

可考虑的真实用途：

- 自动分类和去重公开 Issue，但最终分类由维护者确认。
- 对外部 PR 做第一轮测试分析、风险摘要和回归检查。
- 生成版本变更摘要和迁移说明草稿，由维护者审核。
- 审查 API schema 变化对兼容性的影响。
- 对解析器和写入安全层生成边界测试，再由 CI 验证。
- 在不上传私人词汇内容的前提下，辅助维护文档和公开示例。

不应把额度主要描述为替个人用户生成释义内容；申请重点应是开源维护负担。

## 5. 本项目能形成的生态价值

潜在价值需要通过真实使用验证，目前只作为方向：

- 为墨墨开放 API 提供一个安全、可读、可复用的客户端实现。
- 示范如何处理 dry-run、回读验证、幂等和部分失败等写入安全问题。
- 为批量导入自建释义提供通用格式和可扩展解析器。
- 记录例句 highlight/translation range 等 API 能力边界，减少其他开发者重复试错。
- 在桌面端补充官方 App 的快速查词和用户状态展示流程。

## 6. Codex 在仓库中的正确角色

项目从一开始使用 Codex，但不能让 Codex 制造“维护活动”。正确方式：

- GitHub Issue 先定义真实任务。
- Codex 阅读 Issue 和仓库文档，实施最小改动。
- Codex 创建 Draft PR，提供测试与风险说明。
- 所有者审查、要求修改、决定合并。
- Codex 可以做轻量事实回写，但不自行改写产品阻断项和重大决策。
- PR 数量不是目标，可靠性和维护质量才是目标。

## 7. 申请时机判断

满足以下条件再认真考虑申请：

1. 仓库已公开一段足以产生真实使用和维护记录的时间。
2. 至少有一个可用版本，且有人在所有者之外实际使用。
3. Issue/PR/Release 记录自然形成，而不是为了申请临时补造。
4. 能给出具体数据或有力的生态重要性论证。
5. 能说明 Codex/API 额度会如何直接减轻维护工作。

在此之前，Issue #7 保持开放，用作准备和证据总账，不急于提交表单。
