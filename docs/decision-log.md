## D-010：开发和真实冒烟测试与主账号隔离，防范账号级灾难

**日期：** 2026-08-03  
**状态：** 有效

所有 API 开发、真实写入测试、删除测试、异常恢复和回滚验证，必须只使用所有者的副账号/测试账号。开发与测试环境不得配置、读取或保存主账号 Token；同一进程或配置文件中不得同时存在测试账号和主账号凭证。

这里所说的“主账号不能承担损失风险”，主要是指账号被封禁、账号或数据整体不可用、凭证串号导致批量误操作、不可恢复的大范围删除/覆盖等账号级灾难；并不意味着主账号永远禁止正常的单条新增或经确认的可修正更新。

主账号在 Issue #2 验证阶段只可用于墨墨 App 内的人工只读检查，例如确认另一账号发布的标签内容是否可发现；不得向本项目提供主账号 Token，不得通过项目对主账号执行 create、update 或 delete。

测试账号全部阻断项、账号身份确认、失败恢复和回读验证通过后，主账号接入仍需单独 Issue 和所有者再次明确批准。主账号阶段必须具备：明确显示当前账号身份、批次预览、逐项结果、数量上限、写后回读、停止/失败保护和脱敏日志。更新仅限明确选中的用户自建记录；删除默认不开放。任何无法确认当前 Token 所属账号、预期影响范围或回读结果的情况都必须停止。

## D-011：墨墨自建释义按“新增或替换唯一自建释义”工作

**日期：** 2026-08-03  
**状态：** 有效

按所有者长期实际使用经验，一个单词通常只能维护一条自己的自建释义；添加自建释义后，App 中会以该内容取代/遮盖默认释义的主要展示。因此产品不能把“永远只新增、不更新”作为正式策略。

批量录入时按以下规则处理：

1. 没有用户自建释义：展示将新增的内容，确认后创建。
2. 已存在一条用户自建释义：同时展示“现有内容”和“准备写入内容”，明确询问后更新该记录。
3. 无法确认记录归属、返回多条候选或内容身份有歧义：停止该词，不自动选择或覆盖。
4. 内置默认释义不是 API 更新目标；项目只创建或更新用户自己的自建记录。
5. 每次更新前保留现有内容的脱敏快照，写后回读；可修正的单条内容错误不等同于账号级灾难。

该产品行为和 API 返回形态仍需先在副账号完成真实验证，再用于主账号。

## D-013：v0.1.0 凭证只走隐藏交互输入，取代 #6 的"环境变量/钥匙串"措辞

**日期：** 2026-08-09
**状态：** 有效

Issue #6 的公开门槛原文写的是"Secrets are loaded only from environment variables or the platform keychain"。该措辞早于真实 CLI 的实现，对本项目**过宽**，现予以取代。

`v0.1.0` 的凭证契约为：

- 真实 Token 只能通过隐藏交互式 `getpass` 输入；
- 仅存于进程内存，不持久化；
- 不从命令行参数、环境变量、`.env`、配置文件、剪贴板或系统钥匙串读取；
- 绝不进入 Git、日志、预览、运行报告或审阅 ZIP；
- 只显示 Token 的 16 位 SHA-256 非敏感指纹。

原因：环境变量和 `.env` 会存活到进程之外，泄漏进 shell 历史、子进程环境、崩溃转储和 CI 日志；`getpass` 不会。这一条比通行惯例更严格是刻意的，不得为了"符合常见做法"而放宽。

对应动作：删除 `.env.example`（它暗示了产品并不支持的 Token 加载方式），并同步修正 `SECURITY.md`、`AGENTS.md` 第 5 节和 `CONTRIBUTING.md`。放宽该边界需要新的 Issue 级安全决策。

## D-012：每轮 coding Prompt 必须显式选择模型、思考深度和执行模式

**日期：** 2026-08-03  
**状态：** 有效

本项目采用 `docs/CODEX_REASONING_DEPTH_POLICY.md` 作为 canonical 协议。该协议以 `davidqyc/babyfood@master` 的同名政策为源，按本项目“极小应用、范围应主动收窄”的特征重新设定默认档位。

每一份发给 Codex、Claude Code、Kimi Code 或其他 coding 程序的正式 Prompt，都必须显式写明：实际模型、思考深度、执行模式和一句选择原因；每轮重新判断，不机械继承上一轮。

项目默认：

- 机械 Git、merge、readback 和 ZIP 核验使用 `轻度`；
- 小型 docs 与确定性窄修复使用 `中`；
- 普通实质 coding 与定向 Reviewer 使用 `高`；
- Token、账号隔离、真实写入、response loss、unknown outcome、恢复/回滚或 Reviewer 实质 BLOCK 使用 `极高`；
- `最高` 与 `Ultra` 默认关闭，必须另行说明普通档位不足或并行 ROI。

此前 Issue #2 与 Issue #9 第一版均使用 `高`，与当时完全离线、首次实现且边界清楚的任务相符。PR #10 当前阻断修复因 Reviewer 已 BLOCK，且涉及写入结果未知、恢复状态和凭证防串号，升级为 `极高`、单 Agent。

## D-014：主账号释义录入按显式 opt-in 开放，D-010 的隔离前提已满足

**日期：** 2026-08-09
**状态：** 有效

副账号的 `create` / `update` / 写后回读验证已经完成，D-010 所要求的“测试账号全部阻断项、失败恢复和回读验证通过”前提成立。Issue #51 就是 D-010 所设想的、需要单独 Issue 和所有者再次明确批准的主账号接入步骤；所有者已在 #51 中明确批准把已验证的释义批量录入用于主账号的正常使用。D-010 的历史理由不作废、不改写，本条只在其之上追加这一步。

具体边界：

- 主账号使用必须显式加 `--allow-main-account`；不给该开关时，行为与既有副账号/测试账号策略完全一致。
- 主账号模式还必须给出经复核的主账号标签（`主账号` / `main-account`）；`prod` / `production` 不是个人主账号的同义词。两个条件缺任一都在 Token 提示和传输层创建之前 fail closed。
- 副账号确认串不能授权主账号运行，主账号确认串也不能授权副账号运行。
- 删除能力仍然不开放；仍然没有自动回滚。
- **账号身份仍然是操作者的责任**：当前开放 API 没有身份端点，导入器无法证明 Token 属于哪个账号，因此必须在登录目标主账号的前提下获取 Token。
- `scripts/issue9_live_harness.py` 的副账号门禁不放宽，历史 spike/probe 工具仍然只能用于测试账号。

## D-015：移动端采用轻量 iOS companion，不通过 Mac 局域网代理或云端 relay

**日期：** 2026-08-09
**状态：** 有效

Issue #54 的 macOS 本地日常 UI 已完成真机验收后，Owner 明确选择“轻量 iOS companion”作为下一产品方向。移动端不把当前 Mac localhost 服务暴露到局域网，也不引入接收或保存 Maimemo Token 的云端 relay；目标是让 iPhone 作为独立 on-device companion，在设备本地完成输入、预览、确认，并直接调用同一开放 API。

该移动端只迁移已经验证过的**产品安全语义**，不借机扩大功能：dry-run/Preview 0 POST、CREATE/UPDATE 分离、fresh preflight、stale preview 必须失效、每个变更项最多一次 POST、无 POST 重试、immediate authenticated readback、UPDATE 只针对唯一明确的用户自建记录、ALREADY_MATCHING 零写入、不开放 delete，phrase/example automation 继续 blocked。

D-013 不能被机械照搬成“iOS 自动使用 Keychain”，也不能因为平台原生提供持久化能力就默认保存 Token。iOS 凭证输入和持久化策略必须先在 Issue #56 中单独确认；在新的 iOS 代码路径完成独立评审并获得 Owner 明确授权前，不得用它执行真实主账号写入。
