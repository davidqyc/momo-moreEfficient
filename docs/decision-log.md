# 决策记录

本文件记录已经确认、会影响后续实现的项目级决策。重大改变应先更新对应 GitHub Issue，经所有者确认后再修改本文件。

## D-001：仓库先短期私有，再尽快公开

**日期：** 2026-08-03  
**状态：** 有效

先用极短私有清场期建立凭证保护、完成单条 API 冒烟测试并检查 Git 历史。达到 Issue #6 的公开门槛后转为 Public，不等待全部功能完成。

原因：首次实验存在 Token、私人词条和原始响应泄漏风险；但长期私有不利于真实用户、贡献和开源维护证据形成。

## D-002：GitHub Issue 是任务入口，Codex 以读取和实现为主

**日期：** 2026-08-03  
**状态：** 有效

首轮由 ChatGPT 将大段背景、产品要求和阻断项写入仓库。此后工程任务优先创建/更新 GitHub Issue，Codex 先读取 Issue 和仓库文档，再进行代码实现和轻量事实回写。

Codex 不得自行发明重大产品决策，也不应依赖聊天历史作为唯一依据。

## D-003：批量释义录入优先于桌面查词

**日期：** 2026-08-03  
**状态：** 有效

用户的批量录入过程一次涉及约 8–15 个词，重复操作成本高。先验证 API 并交付安全的释义录入闭环；桌面快速查词作为后续独立能力。

## D-004：释义和例句是两条独立线路

**日期：** 2026-08-03  
**状态：** 有效

例句线路遇到阻断项时，不得拖住释义线路。释义标签及共享发现验证通过后，释义 MVP 可继续；例句保持 blocked，直到自身条件满足。

## D-005：例句的三个条件按阻断级别执行

**日期：** 2026-08-03  
**状态：** 有效

- `MBA`、`BEC`、`GMAT` 可选且伙伴可通过标签发现：绝对阻断。
- 英文例句目标词义位置可可靠标记：绝对阻断。
- 中文翻译字符位置：当前高难度且实质阻断；只有 API 可接收精确范围，或所有者明确接受手工收尾，才可继续。
- 来源/origin：非阻断，但应保留。

## D-009：Codex 文件交付必须附审阅 ZIP，所有者问题必须白话化

**日期：** 2026-08-03  
**状态：** 有效

只要 Codex 在一轮中新增、修改或删除任何实体文件，最终回复必须附带可直接点击的 Markdown ZIP 链接，供所有者转交 ChatGPT 审阅。ZIP 本体只在本地忽略目录生成，不进入 Git；必须报告 SHA-256、大小、文件数、完整性、路径安全及解压回校验结果，并排除凭证、私人数据和构建依赖。

Codex 请求所有者做决策时，必须先用中文白话说明“要决定什么”，再列选项、利弊和明确推荐；请求所有者执行动作时，必须翻译成可直接照做的熟悉步骤，说明预期结果和停止条件。仅抛技术术语、裸命令或无取向的“请选择”不算合格交付。

## D-010：开发和真实冒烟测试与主账号隔离，防范账号级灾难

**日期：** 2026-08-03  
**状态：** 有效

所有 API 开发、真实写入测试、删除测试、异常恢复和回滚验证，必须只使用所有者的副账号/测试账号。开发与测试环境不得配置、读取或保存主账号 Token；同一进程或配置文件中不得同时存在测试账号和主账号凭证。

这里所说的“主账号不能承担损失风险”，主要是指账号被封禁、账号或数据整体不可用、凭证串号导致批量误操作、不可恢复的大范围删除/覆盖等账号级灾难；并不意味着主账号永远禁止正常的单条新增或经确认的可修正更新。

主账号在 Issue #2 验证阶段只可用于墨墨 App 内的人工只读检查，例如确认另一账号发布的标签内容是否可发现；不得向本项目提供主账号 Token，不得通过项目对主账号执行 create、update 或 delete。

测试账号全部阻断项、账号身份确认、失败恢复和回读验证通过后，主账号接入仍需单独 Issue 和所有者再次明确批准。主账号阶段必须具备：明确显示当前账号身份、批次预览、逐项结果、数量上限、写后回读、停止/失败保护和脱敏日志。更新仅限明确选中的用户自建记录；删除默认不开放。任何无法确认当前 Token 所属账号、预期影响范围或回读结果的情况都必须停止。

## D-011：墨墨自建释义按“新增或替换唯一自建释义”工作

**日期：** 2026-08-03  
**状态：** 有效

按所有者长期实际使用经验，一个单词通常只能维护一条自己的自建释义；添加自建释义后，App 中会以该内容取代/遮盖默认释义的主要展示。因此产品不能把“永远只新增、不更新”作为正式策略。

批量录入时按以下规则处理：

1. 没有用户自建释义：展示将新增的内容，确认后创建。
2. 已存在一条用户自建释义：同时展示“现有内容”和“准备写入内容”，明确询问后更新该记录。
3. 无法确认记录归属、返回多条候选或内容身份有歧义：停止该词，不自动选择或覆盖。
4. 内置默认释义不是 API 更新目标；项目只创建或更新用户自己的自建记录。
5. 每次更新前保留现有内容的脱敏快照，写后回读；可修正的单条内容错误不等同于账号级灾难。

该产品行为和 API 返回形态仍需先在副账号完成真实验证，再用于主账号。
